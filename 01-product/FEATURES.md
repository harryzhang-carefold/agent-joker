## 1. 模块一：基础功能（BASE）

### BASE-01 用户管理
- **描述**：用户的创建、修改、禁用/启用、查询（含重置密码）；用户是平台基本主体。对应 BRIEF §2-基础功能「用户管理」（B01）。
- **来源**：【用户明确要求】（B01）
- **验收要点**：
  1. 管理员可创建用户（用户名、初始密码、所属租户、分配角色），创建后出现在用户列表；
  2. 禁用用户后该用户无法登录，且其业务接口请求被拒绝；
  3. 支持管理员重置用户密码。
- **数据/依赖提示**：用户实体（租户、用户名、密码凭据、角色引用、状态、创建/更新时间）；依赖 BASE-02 角色、BASE-07 多租户模型。

### BASE-02 角色管理
- **描述**：角色的创建、修改、删除、查询；角色是权限集合的载体。对应 BRIEF §2-基础功能「角色管理」（B02）。
- **来源**：【用户明确要求】（B02）
- **验收要点**：
  1. 可创建角色并为其关联权限点，可查看某角色的权限清单；
  2. 角色的增删改即时生效于用户权限计算（改角色权限后，该角色用户的可用权限随之变化）；
  3. 用户可分配/变更角色。
- **数据/依赖提示**：角色实体、角色-权限映射、用户-角色映射；依赖 BASE-03。

### BASE-03 权限管理
- **描述**：定义并维护权限点（接口级/资源级），将权限点授予角色；提供统一权限校验能力供各模块与 BFF 调用。对应 BRIEF §2-基础功能「权限管理」（B03）；BFF「校验用户是否有权限访问目标 Agent」（G02）消费本模块能力。
- **来源**：【用户明确要求】（B03，G02 消费）
- **验收要点**：
  1. 可定义权限点（编码+描述）并关联到角色；
  2. 用户有效权限 = 其全部角色权限的并集（可验证：拥有两个角色的用户可使用两个角色的权限）；
  3. 提供权限校验 API（输入：用户+目标资源/操作 → 允许/拒绝），被 BFF 的 Agent 访问校验（BFF-05）实际调用。
- **数据/依赖提示**：权限点实体、角色-权限映射；Agent 访问授权需可表达（如权限点 "agent:use:<id>" 或 agent 访问关系表——设计文档明确）。

### BASE-04 登入
- **描述**：用户以用户名+密码登录，成功后获得 Access Token。对应 BRIEF §2-基础功能「登入登出」（B04）。
- **来源**：【用户明确要求】（B04）；令牌形式为【推测】（见 BASE-09）
- **验收要点**：
  1. 正确用户名+密码 → 返回 Access Token，可凭该 token 调用业务接口；
  2. 密码错误 → 拒绝且不签发 token；
  3. token 中携带 tenant_id、user_id、scopes（可被 BFF 提取，见 BFF-05）。
- **数据/依赖提示**：会话/token（无状态 JWT + 刷新令牌记录，见 BASE-09）；依赖用户表。

### BASE-05 登出
- **描述**：用户主动登出，令牌失效。对应 BRIEF §2-基础功能「登入登出」（B04）。
- **来源**：【用户明确要求】（B04）；令牌失效机制为【推测】（见 BASE-09，与 BASE-04 同属 P2 令牌机制推测）
- **验收要点**：
  1. 登出后原 Access Token 不再可用（立即失效，或刷新令牌失效+访问令牌到期自然失效——策略在设计文档明确且行为与文档一致）；
  2. 登出操作被记录到接口操作日志（BASE-06）。
- **数据/依赖提示**：若 JWT 无状态需刷新令牌吊销机制（黑名单表或刷新令牌表）；依赖 BASE-04/09。

### BASE-06 接口操作日志
- **描述**：记录接口操作日志：谁、何时、调用了哪个接口、关键参数、结果状态。对应 BRIEF §2-基础功能「接口操作日志」（B05）。
- **来源**：【用户明确要求】（B05）
- **验收要点**：
  1. 调用任一业务接口（登录、创建知识库、agent 对话等）后，可在操作日志中查到对应记录（操作者、时间、接口、状态码）；
  2. 日志支持按时间范围/用户/接口筛选查询；
  3. 敏感字段（token、密码）在日志中脱敏；
  4. 日志写入失败不阻断业务接口主流程（容错）。
- **数据/依赖提示**：操作日志实体（租户、用户、接口路径、方法、状态码、时间、参数摘要）；经统一拦截器/中间件写入。

### BASE-07 多租户模型
- **描述**：平台为多租户：登录账号属于某租户，业务数据按 tenant_id 行级隔离。对应 BRIEF §2-BFF「提取 tenant_id」（G02）及 §4 推测项 P3。
- **来源**：【推测】（BRIEF §4-P3；理由：BRIEF 原话提到 tenant_id 但未指定租户模型，团队提出所有业务表带 tenant_id 行级隔离、登录账号属某租户，闭环可演示）
- **验收要点**：
  1. 两个不同租户的用户互不可见对方的知识库、Agent、会话（跨租户查询返回空或 403）；
  2. 用户即使直接猜测资源 ID 也无法访问其他租户资源；
  3. 所有业务表含 tenant_id 且有相应索引（DB 设计文档与实际 schema 可验证）。
- **数据/依赖提示**：租户实体；全部业务表加 tenant_id；框架级强制 tenant 过滤（建议）；闭环演示需可创建 2 个测试租户（种子数据或管理员接口）。

### BASE-08 前端管理界面
- **描述**：Web 管理控制台，覆盖：用户/角色/权限管理、知识库管理（原文查看、chunk 编辑）、MCP/Skills/Agent 管理、会话列表与对话详情。对应 BRIEF §4 推测项 P1。
- **来源**：【推测】（BRIEF §4-P1；理由：BRIEF 要求原文查看、chunk 编辑、管理操作、会话列表等能力，暗示需要 Web 管理控制台；技术栈 Vue3 或 React 由团队选型并记录 DECISIONS.md）
- **验收要点**：
  1. 在 UI 中可完成主闭环操作：创建用户/角色/权限 → 创建知识库 → 上传文档 → 查看原文/编辑 chunk → 创建 Agent（勾选 LLM/知识库/MCP 工具/Skills）→ 发起对话 → 查看会话列表与对话详情；
  2. UI 操作全部走带 token 的后端 API，无直连数据库；
  3. 技术栈选型记录在 DECISIONS.md。
- **数据/依赖提示**：无新增持久化实体（前端工程）；依赖各模块 API；页面清单 = BRIEF P1 原话所列。

### BASE-09 Access Token 机制（JWT 访问/刷新令牌）
- **描述**：认证方案具体化：密码登录 + JWT Access Token（含 tenant_id、user_id、scopes、有效期）+ 刷新令牌续期。对应 BRIEF §4 推测项 P2 与 §2-BFF「Access Token」（G01/G02）。
- **来源**：【推测】（BRIEF §4-P2；理由：BRIEF 仅提「Access Token（JWT 倾向）」，登录方式与令牌形态未指定，团队提出密码登录 + JWT 访问/刷新令牌，闭环可演示）
- **验收要点**：
  1. Access Token 有有效期，过期请求被拒绝（401）；
  2. 过期后凭刷新令牌可换取新 Access Token，无需重新登录；
  3. BFF 可验证 token 并提取 tenant_id、user_id、scopes；篡改/伪造 token 被拒绝。
- **数据/依赖提示**：JWT claim 结构（tenant_id、user_id、scopes、exp、jti）；若刷新令牌有状态需刷新令牌记录表；依赖 BASE-04/05、BFF-01。

### 1.1 验收要点汇总
1. 用户/角色/权限三元组可在 UI 管理与关联，用户有效权限 = 角色权限并集（接口可验证）。
2. 登录→获 token→访问接口→登出全流程可用；密码错误被拒；token 携带三要素且可被 BFF 提取；过期 401、刷新可用。
3. 两个租户用户数据完全隔离：跨租户不可见、不可访问（含直接猜 ID）。
4. 任意接口调用留有操作日志（操作者/时间/接口/状态），可按时间/用户/接口检索，敏感字段脱敏。
5. 前端管理界面可完成上述全部管理闭环（见 BASE-08）。

## 2. 模块二：存储模块（STORE）

### STORE-01 保存文件——本地目录后端
- **描述**：文件保存至本地目录，存储路径通过配置文件配置。对应 BRIEF §2-存储「保存文件：支持配置本地存储路径……配置文件可配置」（S01）。
- **来源**：【用户明确要求】（S01）
- **验收要点**：
  1. 配置文件指定本地路径后上传文件，文件实际落盘到该目录；
  2. 修改路径配置（重启生效即可）后新上传落盘到新路径。
- **数据/依赖提示**：文件实体（文件名、存储路径、大小、类型、租户、上传者、时间、后端类型）；本地路径来自配置文件。

### STORE-02 保存文件——云存储后端（GCS / 阿里云 OSS）
- **描述**：支持将文件保存到 Google Cloud Storage 或阿里云 OSS。对应 BRIEF §2-存储「保存文件：……云存储（Google Cloud Storage、阿里云 OSS）」（S01）。
- **来源**：【用户明确要求】（S01）
- **验收要点**：
  1. 配置切换到 GCS 或 OSS 后上传文件，文件出现在对应 bucket 中，且可通过统一访问接口读回；
  2. 凭证、bucket、endpoint 均在配置文件，不落代码。
- **数据/依赖提示**：文件实体（云后端需 bucket/prefix/key）；凭证存配置文件（不进 DB）；后端抽象层（统一存储 SDK 接口）。

### STORE-03 存储后端配置切换
- **描述**：本地 / GCS / OSS 通过配置文件切换，不改代码。对应 BRIEF §2-存储「配置文件可配置」（S01）。
- **来源**：【用户明确要求】（S01）
- **后端切换策略（设计裁定，2026-09-22）**：后端切换采用**保留原后端访问策略**——按文件实体行内 backend 字段分派访问，既有文件保留在原后端读取，不做自动迁移。
- **验收要点**：
  1. 通过配置文件切换后端（至少重启后生效），上传与访问均正常；
  2. 切换后新文件落到新后端并工作正常；
  3. 既有文件按行内 backend 分派，仍可经统一访问接口（STORE-04）从原后端读取（保留原后端访问、不自动迁移——上述设计裁定）。
- **数据/依赖提示**：存储配置（类型、路径/bucket/endpoint、凭证）；文件实体记录后端类型以支持混合后端定位旧文件。

### STORE-04 统一文件访问接口
- **描述**：提供统一文件访问 API，按文件名称访问；本地目录存储时调用方不直接接触原始路径，一律走该接口。对应 BRIEF §2-存储「访问文件：本地目录存储时需开发统一接口，可根据文件名称访问」（S02）。
- **来源**：【用户明确要求】（S02）
- **验收要点**：
  1. 按文件名（限本租户）调用访问接口可获取文件内容；
  2. 同一 API 在本地后端与云后端下行为一致（调用方无需感知后端差异）；
  3. 文件不存在 → 404；跨租户访问 → 403，错误信息清晰；
  4. 同名文件策略（覆盖或唯一后缀/版本）在设计文档明确，行为与文档一致。
- **数据/依赖提示**：文件访问 API（文件名+租户 → 内容/URL）；文件实体是"文件名→路径"映射的关键；文件名唯一性范围（租户内/全局）设计明确。

### STORE-05 文件上传记录
- **描述**：保存文件上传记录。对应 BRIEF §2-存储「保存文件上传记录」（S03）。
- **来源**：【用户明确要求】（S03）
- **验收要点**：
  1. 任意一次上传（API 直接上传、MCP 工具上传、agent 交互上传）后，均可在上传记录列表查到该记录（文件名、上传者、租户、时间、大小、来源、状态）；
  2. 记录支持按时间范围/文件名/上传者筛选。
- **数据/依赖提示**：上传记录实体（文件引用、上传者、租户、来源（API/MCP/agent/知识库上传）、时间、大小、状态、错误信息）。

### STORE-06 文件上传 MCP 工具
- **描述**：将文件上传接口注册为 MCP 工具，供 agent 上传文件。对应 BRIEF §2-存储「上传和访问文件接口都可注册为 MCP 工具」（S04），并被第三方 agent（TA02）消费。
- **来源**：【用户明确要求】（S04，TA02 消费）
- **验收要点**：
  1. 平台存储上传工具出现在 MCP 工具列表（平台内置工具或以内部 MCP server 形式注册——形态在设计文档明确）；
  2. agent 调用该工具可成功上传文件，文件落存储模块并生成上传记录（STORE-05）；
  3. 调用经过 BFF 工具拦截（BFF-06/07/09），token 注入校验生效。
- **数据/依赖提示**：工具定义（入参：文件名+内容；出参：文件 ID/名称）；依赖 STORE-01..05、MCP 模块（MCP-02 工具列表）、BFF 拦截链。

### STORE-07 文件访问/查询 MCP 工具
- **描述**：将文件访问/查询接口注册为 MCP 工具，供 agent 查询文件。对应 BRIEF §2-存储（S04）及第三方 agent「平台提供上传文档和查询文档的 MCP 工具」（TA02）。
- **来源**：【用户明确要求】（S04，TA02 消费）
- **验收要点**：
  1. 查询工具可被 agent 调用，按文件名/条件返回文件内容或文件列表；
  2. 仅返回本租户文件（token 决定租户，跨租户返回空或 403）；
  3. 调用经过 BFF 工具拦截。
- **数据/依赖提示**：依赖 STORE-04 与上传记录实体；工具定义（入参：文件名/查询条件；出参：内容/列表）。

### 2.1 验收要点汇总
1. 同一文件分别在本地与 GCS/OSS 后端（切换配置）上传，均物理存在于对应后端，且用同一统一 API 可访问（S01/S02/S03）。
2. 按文件名访问：本租户得内容；不存在 404；跨租户 403；同名文件行为与设计文档一致（S02）。
3. 任意来源（API/MCP/agent）的上传都留有上传记录，可筛选检索（S03）。
4. 上传、查询两个 MCP 工具可被 agent 调用，租户隔离生效，拦截链生效（S04/TA02）。

## 3. 模块三：LLM 节点（LLM）

### LLM-01 LLM endpoint 信息维护
- **描述**：维护 LLM endpoint 信息（名称、URL、模型名、鉴权参数、参数配置），供 Agent 配置时从列表勾选。对应 BRIEF §2-LLM 节点「LLM endpoint 信息维护」（L01）。
- **来源**：【用户明确要求】（L01）
- **验收要点**：
  1. 可新增/修改/删除/查询 LLM endpoint；
  2. Agent 创建/编辑时 LLM 选项列表来源于此（勾选即用）；
  3. 提供连通性/调用测试（可选）——发起测试调用返回模型应答或明确错误。
- **数据/依赖提示**：endpoint 实体（租户、名称、base_url、模型名、API 凭证/密钥、默认参数如 temperature、启用状态）；被 Agent 配置引用（Agent 实体）。

### LLM-02 embedding 模型信息维护
- **描述**：维护 embedding 模型信息，供知识库选择 embedding 模型。对应 BRIEF §2-LLM 节点「embedding 模型信息维护」（L02）。
- **来源**：【用户明确要求】（L02）
- **验收要点**：
  1. 可新增/修改/删除/查询 embedding 模型（名称、endpoint/本地路径、模型标识、维度等）；
  2. 创建/配置知识库时可选的 embedding 模型列表来源于此。
- **数据/依赖提示**：embedding 模型实体（维度、来源（API/本地）、凭证）；被 RAG 知识库实体引用。

### LLM-03 reranker 模型信息维护
- **描述**：维护 reranker 模型信息，供知识库检索时可选使用。对应 BRIEF §2-LLM 节点「reranker 模型信息维护」（L03）。
- **来源**：【用户明确要求】（L03）
- **验收要点**：
  1. 可新增/修改/删除/查询 reranker 模型（名称、endpoint/本地路径、模型标识）；
  2. 知识库检索配置中 rerank 模型选项列表来源于此；不选择时检索跳过 rerank（见 RAG-08）。
- **数据/依赖提示**：reranker 模型实体；被 RAG 知识库检索配置引用（可选引用）。

### 3.1 验收要点汇总
1. 三类模型信息（endpoint/embedding/reranker）均可 CRUD 且列表可查（L01–L03）。
2. Agent 与知识库配置界面中的下拉选项与 LLM 节点维护的数据一致（勾选来源正确）。
3. 修改/删除某 endpoint 后，引用它的配置行为与删除策略一致（策略在设计文档明确，如禁用代替硬删）。

## 4. 模块四：RAG 知识库（RAG）

### RAG-01 创建知识库
- **描述**：创建知识库（名称、描述、可选配置：embedding 模型、检索参数、库级 tag 等）；文档级 tag 在上传/管理文档时设置（见 D-A 两级判定）。对应 BRIEF §2-RAG「创建知识库」（R01）。
- **来源**：【用户明确要求】（R01）
- **验收要点**：
  1. 创建知识库后出现在知识库列表，含名称/描述/文档数/配置摘要；
  2. 创建时可选择 embedding 模型（来自 LLM-02 列表）；
  3. 知识库可设置/修改库级 tag（如 `official`，见 AGENT-05 引用规则）；
  4. 文档级 tag 可在文档上传时设置或后续单独修改（文档 tag 可空，NULL 时继承库级 tag 参与判定——裁定 D-A，用户裁定 2026-09-22）；
  5. 支持删除/编辑知识库（删除策略：文档与向量级联处理，设计文档明确）。
- **数据/依赖提示**：知识库实体（租户、名称、描述、embedding 模型引用、库级 tag、检索默认参数、状态）；文档实体含文档级 tag 字段（可空，NULL 继承库级）；依赖 LLM-02。

### RAG-02 上传文档（6 种类型，走存储模块）
- **描述**：向知识库上传 txt、word、excel、pdf、png、jpg 文档；文件经存储模块 API 保存。对应 BRIEF §2-RAG「上传文档类型：txt、word、excel、pdf、png、jpg」+「上传文档（调用存储模块 API）」（R02、R04）。
- **来源**：【用户明确要求】（R02、R04）
- **验收要点**：
  1. 六种类型均可上传成功，文档记录进入知识库；
  2. 非支持类型（如 .exe）被拒绝，有明确错误；
  3. `.doc` 旧格式不在支持范围（"word" 仅指 `.docx`）：上传 `.doc` 返回 422 拒绝并提示转 `.docx`（设计裁定，2026-09-22）；
  4. 上传调用存储模块 API（可在上传记录中查到来源=知识库的 STORE 记录）；
  5. 上传后进入解析流水线（RAG-03/04）并产生 chunk。
- **数据/依赖提示**：文档实体（租户、知识库引用、文件名、存储引用、类型、状态（解析中/成功/失败）、错误信息）；依赖 STORE 模块。

### RAG-03 文档视觉解析（图片/扫描 PDF/文档内图片）
- **描述**：图片、扫描版 PDF 及普通文档中的部分图片，需通过 LLM 视觉能力提供文档内容（主要是论文公式、图表）。对应 BRIEF §2-RAG 视觉解析条（R03）；具体解析实现方式为【推测】范围（P5）。
- **来源**：【用户明确要求】（R03，需求本身）；解析流水线实现【推测】（BRIEF §4-P5；理由：OCR/版面分析/视觉 LLM 的具体实现方式如解析库选型用户未指定，由团队设计）
- **验收要点**：
  1. 上传含公式的图片（如论文公式截图 png）后，chunk 列表可见公式的文字化内容；
  2. 上传扫描版 PDF（纯图像）后，chunk 包含 OCR/视觉识别出的文字；
  3. 上传含插图/图表的普通 PDF 后，图表内容被描述性文字化并进入 chunk（或标记为图片引用——策略设计文档明确且行为一致）；
  4. 解析使用的视觉能力基于已维护的 LLM endpoint（多模态）或团队选型的解析方案（选型记录 DECISIONS.md）。
- **数据/依赖提示**：文档解析产物（chunk 文本、图片引用/描述、解析方式标记）；依赖 LLM 节点（多模态 endpoint）、解析库（选型）。

### RAG-04 切分策略（定长/父子/语义/结构化/表格）
- **描述**：文档切分支持五种策略：定长、父子、语义、结构化/文档树、表格。对应 BRIEF §2-RAG「切分策略：定长、父子、语义、结构化/文档树、表格」（R05）。
- **来源**：【用户明确要求】（R05）
- **验收要点**：
  1. 同一文档分别以五种策略切分，均产生结构合理的 chunk（如表格策略对 excel/表格 PDF 产出表格级 chunk）；
  2. 策略可在文档/知识库级别配置并重新切分；
  3. 父子策略产出父块与子块两级且互相引用（检索可回父块——见 RAG-09 定位）；
  4. 每种策略的参数（长度、步长、分隔符等）可配置，缺省值在文档中明确。
- **数据/依赖提示**：chunk 实体需表达：父 chunk 引用、切分策略类型、chunk 顺序、（表格）结构化内容；依赖向量库（P4）。

### RAG-05 原文档查看 + 手动修改 chunk
- **描述**：支持原文档查看，支持手动修改切分后的 chunk 内容。对应 BRIEF §2-RAG「支持原文档查看，支持手动修改切分后的 chunk 内容」（R06）。
- **来源**：【用户明确要求】（R06）
- **验收要点**：
  1. 知识库文档详情页可查看原文（文本渲染/文件预览，至少内容可读）；
  2. 修改某 chunk 文本并保存后，检索结果返回新内容（向量随之更新）；
  3. chunk 编辑有列表视图（顺序+内容+位置）；
  4. 修改操作可留痕（审计：操作人/时间，可依赖 BASE-06 或文档级审计字段）。
- **数据/依赖提示**：chunk 实体（可编辑内容、更新人/时间）；向量更新联动；原文档经 STORE-04 访问。

### RAG-06 检索：embedding 模型选择
- **描述**：知识库支持选择 embedding 模型（检索时按所选模型向量化查询）。对应 BRIEF §2-RAG「支持选择 embedding 模型」（R07）。
- **来源**：【用户明确要求】（R07）
- **验收要点**：
  1. 知识库配置/检索时可选 embedding 模型（来自 LLM-02）；
  2. 查询以所选模型向量化后检索，同库不同模型选择按所选生效（或设计文档明确"切换模型需重嵌入"策略并验证该行为）。
- **数据/依赖提示**：知识库实体存 embedding 模型引用；chunk 向量与其模型维度绑定（换模型需重嵌入——设计明确）。

### RAG-07 检索：rerank 模型（可选）
- **描述**：检索支持选择 rerank 模型（可选）。对应 BRIEF §2-RAG「rerank 模型（可选）」（R07）。
- **来源**：【用户明确要求】（R07）
- **验收要点**：
  1. 配置 reranker 后，检索结果按 rerank 分数排序（分数字段可见）；
  2. 不配置时检索正常（纯向量+阈值）；
  3. rerank 模型来自 LLM-03 列表。
- **数据/依赖提示**：检索配置（reranker 引用，可空）；检索结果记录 rerank score。

### RAG-08 检索：topK 与阈值
- **描述**：支持设置 topK、阈值（相似度/分数阈值过滤）。对应 BRIEF §2-RAG「支持设置 topK、阈值」（R08）。
- **来源**：【用户明确要求】（R08）
- **设计决策（2026-09-22，非推测）**：rag_search API 支持单次检索级 topK/threshold 覆盖参数，未传时回落到知识库默认值（单次覆盖默认）。
- **验收要点**：
  1. 设置 topK=N 时最多返回 N 条；
  2. 设置阈值后低于阈值的 chunk 被过滤（如阈值调高至 1.0 则返回 0 条）；
  3. 参数可在知识库默认级与单次检索级设置：单次检索传入 topK/threshold 覆盖参数时按传入值生效，未传时按知识库默认值生效（设计决策，2026-09-22）。
- **数据/依赖提示**：检索配置（topK、阈值）；检索结果含 score。

### RAG-09 检索返回 chunk 索引与原文档位置（反向定位）
- **描述**：检索返回 chunk 索引及所在原文档位置，用于反向定位内容位置。对应 BRIEF §2-RAG「支持检索返回 chunk 索引及所在原文档位置，用于反向定位内容位置」（R09）。
- **来源**：【用户明确要求】（R09）
- **验收要点**：
  1. 检索结果的每条 chunk 携带：chunk 索引 + 所在文档 + 位置信息（页码/章节/字符偏移/块序号——形式设计文档明确）；
  2. 凭该位置信息可定位原文：打开原文档查看页跳转到对应位置（或高亮）；
  3. 反向定位用于引用链接（AGENT-05 回复末尾的来源链接跳至原文对应位置）。
- **数据/依赖提示**：chunk 实体含位置字段（文档引用、页码/偏移/章节）；文档查看页支持定位跳转参数。

### RAG-10 知识库查询 MCP 工具
- **描述**：知识库支持 MCP server，可将知识库相关查询接口做成 MCP 工具。对应 BRIEF §2-RAG「支持 MCP server，可将知识库相关查询接口做成 MCP 工具」（R10）。
- **来源**：【用户明确要求】（R10）
- **验收要点**：
  1. 平台提供知识库检索的 MCP 工具（工具入参含查询、知识库范围、topK 等），出现在工具列表中；
  2. agent 调用该工具可返回 chunk 内容 + 位置信息（RAG-09）+ 引用文档信息（供 AGENT-05 生成引用）；
  3. 工具受租户隔离与 BFF 拦截约束。
- **数据/依赖提示**：检索 MCP 工具定义；返回体含（chunk 文本、chunk 索引、文档 ID/名称、位置、分数、tag）；依赖 RAG-08/09、MCP-02、BFF 拦截。

### RAG-11 切分对比查看（原文档-chunk 双向联动）
- **描述**：文档切分完成后，提供左右分栏对比查看视图——左栏原文档（txt/word/excel/pdf/图片 渲染展示），右栏 chunk 切片列表；支持双向联动定位。对应用户 2026-09-22 新增需求原话："上传文档切分之后，可对比查看原文档（左边元文档，右边chunk切片）"。
- **来源**：【用户明确要求】（用户后续新增需求，2026-09-22；非推测，不计入 BRIEF §2 45 标准 ID 口径，见 10.1 下方"用户后续新增需求"区）
- **交互**：
  1. 点击右栏某 chunk → 左栏定位到该 chunk 对应的原文位置并高亮；
  2. 点击左栏原文某位置 → 右栏定位到包含该位置的 chunk（双向联动）。
- **验收要点**：
  1. 六类文档（txt、word、excel、pdf、png、jpg）切分完成后均可打开对比视图（左栏渲染展示、右栏 chunk 列表）；
  2. chunk→原文定位准确：点击 chunk 后左栏高亮位置与该 chunk 在 `rag_chunks` 表中的位置信息（pos/chunk_index 等）一致；
  3. 原文→chunk 反向定位正确：点击左栏某原文位置，右栏定位到的 chunk 确实包含该位置；
  4. 手动修改某 chunk 内容并保存后（RAG-05），对比视图中该 chunk 实时展示新内容（无需重新切分或刷新后丢失）。
- **数据/依赖提示**：复用 chunk 实体已有位置字段（RAG-04/RAG-09 数据/依赖提示：父 chunk 引用、顺序、pos/位置）；左栏原文档经 STORE-04 统一文件访问接口读取渲染；依赖 RAG-05（chunk 手动修改）、RAG-09（位置信息）、STORE-04。接口细节（对比视图数据接口、定位参数形式）以章北海在 ARCHITECTURE 的定义为准，本功能点不定义接口。

### 4.1 验收要点汇总
1. 建库→上传 6 类型文档（走存储模块并留上传记录）→解析（图片/扫描/文档内图片视觉化）→按 5 种策略切分，全链路跑通（RAG-01..05）。
2. 原文查看 + chunk 手改后检索返回新内容；chunk 列表含顺序与位置（RAG-05）。
3. 检索按所选 embedding/rerank/topK/阈值生效，结果带 chunk 索引与原文位置，可跳转原文定位（RAG-06..09）。
4. 知识库检索 MCP 工具可被 agent 调用，返回含引用定位信息，租户隔离与拦截生效（RAG-10）。
5. 切分对比查看：六类文档均可打开左右分栏视图，chunk↔原文双向联动定位准确（与 chunk 位置信息一致），chunk 手改后视图实时更新（RAG-11，用户 2026-09-22 新增）。

## 5. 模块五：MCP（MCP）

### MCP-01 通过 URL 注册 MCP server（支持多个）
- **描述**：支持通过 URL 注册 MCP server，且可注册多个。对应 BRIEF §2-MCP「支持通过 URL 注册 MCP server，支持注册多个」（M01）。
- **来源**：【用户明确要求】（M01）
- **验收要点**：
  1. 填写 URL（+名称等）可注册一个 MCP server，注册后出现在 server 列表；
  2. 可注册多个 server，各自独立管理；
  3. 支持编辑/删除已注册 server；删除/编辑走 MCP-03 关联提示流程；
  4. 连通性可检测（注册时或按需发起 tools/list 拉取，失败有明确错误）。
- **数据/依赖提示**：MCP server 实体（租户、名称、URL、协议/传输类型（如 SSE/stdio-HTTP）、状态、最后探测时间、凭证）；被 Agent 配置引用。

### MCP-02 MCP server 工具列表 + 禁用/启用/删除
- **描述**：支持显示每个 MCP server 的工具列表，支持对工具进行禁用、启用、删除等操作。对应 BRIEF §2-MCP「支持显示每个 MCP server 的工具列表，支持禁用、启用、删除等操作」（M02）。
- **来源**：【用户明确要求】（M02）
- **验收要点**：
  1. 进入某 server 详情可见其工具列表（名称、描述、入参 schema，来自远端 tools/list）；
  2. 工具可禁用/启用：禁用后 agent 侧不可调用（工具列表勾选不出现或调用被拒），启用后恢复；
  3. 工具可删除（从平台注册中移除，不删除远端工具），删除后不可选；
  4. 平台内置工具（存储上传/查询、知识库检索）也在工具列表可见（来源标记为平台内置）。
- **数据/依赖提示**：工具实体/缓存（server 引用、工具名、schema 快照、启用状态、来源（远端/平台内置）、更新时间）；agent 工具勾选引用工具 ID。

### MCP-03 删除/禁用操作的关联调用方提示
- **描述**：删除、禁用等操作需提示可能存在关联的调用方。对应 BRIEF §2-MCP「删除、禁用等操作需提示可能存在关联的调用方」（M03）。
- **来源**：【用户明确要求】（M03）
- **验收要点**：
  1. 删除/禁用某 MCP server 或工具时，若存在引用它的 Agent（或其他调用方），界面/接口明确提示"存在 N 个关联调用方：<列表>"并要求确认；
  2. 确认后操作生效，关联 Agent 的工具配置同步更新（工具不可选或调用被拒，行为与设计一致）；
  3. 无关联调用方时可直接操作（无提示或提示 0 个）。
- **数据/依赖提示**：需可查询引用关系：Agent 配置中的工具/server 勾选关系（agent-工具映射表）；提示数据来自该关系查询。

### 5.1 验收要点汇总
1. 通过 URL 注册多个 MCP server，列表可见、可编辑（MCP-01）。
2. 每个 server 工具列表（含 schema）可见；工具禁用后 agent 不可调用、启用恢复、删除不可选；平台内置工具同列（MCP-02）。
3. 删除/禁用有引用方时出现关联调用方提示并可确认；确认后关联 Agent 行为正确（MCP-03）。

## 6. 模块六：Skills（SKILL）

### SKILL-01 手动添加 / 上传 skill，维护名称内容
- **描述**：支持手动添加、上传 skill，维护 skill 名称、内容等信息。对应 BRIEF §2-Skills「支持手动添加、上传 skill，维护 skill 名称、内容等信息」（K01）。
- **来源**：【用户明确要求】（K01）

## 8. 模块八：BFF 网关（BFF）

### BFF-01 统一鉴权（Access Token）
- **描述**：BFF 作为统一入口，对所有请求做统一鉴权（校验 Access Token 有效性）。对应 BRIEF §2-BFF「负责统一鉴权（Access Token）」（G01）。
- **来源**：【用户明确要求】（G01）
- **验收要点**：
  1. 无 token / 无效 token 请求 → 401，且所有受保护接口（管理、对话、工具）均被拦截；
  2. 有效 token 请求通过鉴权进入后续流程；
  3. 各业务服务不各自重复实现 token 校验（BFF 统一校验后透传身份——架构文档体现）。
- **数据/依赖提示**：依赖 BASE-09（JWT 验证）；BFF 为所有 API 前置层。

### BFF-02 流量控制
- **描述**：BFF 负责流量控制（限流/配额）。对应 BRIEF §2-BFF「流量控制」（G01）。
- **来源**：【用户明确要求】（G01）
- **验收要点**：
  1. 超过限流阈值的请求被拒绝（429 或排队，策略设计文档明确）；
  2. 限流维度可验证（如按用户/租户/接口之一生效：压测单用户超阈值被限，其他用户不受影响）；
  3. 限流配置可在配置文件/API 调整并即时生效。
- **数据/依赖提示**：限流配置（维度、阈值、窗口）；计数存储（redis）；配置可持久化。

### BFF-03 API 路由
- **描述**：BFF 负责 API 路由（将请求路由到对应后端服务/引擎）。对应 BRIEF §2-BFF「API 路由」（G01）。
- **来源**：【用户明确要求】（G01）
- **验收要点**：
  1. 不同前缀/端点的请求被正确路由（管理 API→管理服务、chat API→agent 引擎等，路由表在架构文档列出）；
  2. 未知路径返回 404 且有清晰错误；
  3. 路由变更（新增模块端点）无需改 BFF 代码（配置化路由——设计文档明确该机制）。
- **数据/依赖提示**：路由配置表（路径模式→目标服务）。

### BFF-04 协议转换（OpenAI 兼容格式）
- **描述**：将各引擎响应统一为 OpenAI 兼容格式。对应 BRIEF §2-BFF「协议转换（将各引擎响应统一为 OpenAI 兼容格式）」（G01）。
- **来源**：【用户明确要求】（G01）
- **验收要点**：
  1. 简易 agent 与第三方 agent 的对话响应均符合 OpenAI Chat Completions 兼容格式（字段：id/object/choices/message/content/usage 等，流式 SSE 与块式均可用）；
  2. 标准 OpenAI SDK/客户端可直接对接 BFF chat 端点（用官方 SDK 发请求可跑通）；
  3. 工具调用在 OpenAI 格式中的表达（tool_calls 字段）正确。
- **数据/依赖提示**：响应适配层（各引擎原始响应→OpenAI schema）；流式/块式双模式。

### BFF-05 统一鉴权与多租户隔离（Agent 访问权限校验）
- **描述**：agent 的 chat 接口接收请求头 Access Token，提取 tenant_id、user_id 和 scopes；校验用户是否有权限访问目标 Agent（如普通员工只能用客服 Agent，管理员能用数据分析 Agent）。对应 BRIEF §2-BFF「统一鉴权与多租户隔离」（G02）。
- **来源**：【用户明确要求】（G02）；多租户模型本身见 BASE-07【推测】（P3）
- **验收要点**：
  1. chat 请求头 token 被提取出 tenant_id/user_id/scopes（日志/trace 中可见解析结果）；
  2. 普通员工（角色仅授权客服 Agent）调用数据分析 Agent → 拒绝（403），调用客服 Agent → 成功；
  3. 跨租户访问（A 租户 token 调 B 租户 agent）→ 拒绝；
  4. 权限校验调用 BASE-03 的权限能力（架构文档体现）。
- **数据/依赖提示**：agent 访问授权数据（权限点 "agent:use:<id>" 或 agent-角色关系表）；依赖 BASE-03、BASE-07。

### BFF-06 工具调用统一拦截（Tool Call Interceptor）
- **描述**：「工具调用」定义为 **MCP 工具调用**（含平台内置 MCP 工具 upload_doc/query_doc/rag_search 与通过 URL 注册的外部 MCP server 的工具），此类调用必须经过 BFF 统一拦截（Tool Call Interceptor）。对应 BRIEF §2-BFF「统一工具执行拦截（Tool Call Interceptor）：Agent 工具调用必须经过 BFF 统一拦截」（G03）。
- **拦截边界（裁定 D-B，用户裁定 2026-09-22）**：拦截范围 = ①agent 对接业务系统（业务系统 AI chat / 业务系统调用 agent 能力，统一经 BFF 网关）+ ②MCP 工具调用（经 BFF ToolInterceptor 统一拦截：scope 校验、Access Token 强制注入、机器凭证代理执行）。**非拦截范围**：简易 agent 在 agent 管理平台内部对平台内部服务的直接 API 调用（RAG 检索、文件上传/下载等）属平台内部服务调用，**不产生 tool_call 拦截事件**，但必须保留：a) 用户身份校验（tenant/scope）；b) (agent_id, kb_id) 在 agent_knowledge_bases 勾选校验（未勾选 403）；c) 落 trace 为 rag/file 事件。
- **来源**：【用户明确要求】（G03）
- **验收要点**：
  1. 简易 agent 与第三方 agent 的任一 **MCP 工具调用**（含平台内置 upload_doc/query_doc/rag_search），trace 中均可看到 BFF tool_call 拦截记录，100% 覆盖（无绕过路径）；**排除项**：RAG 检索/文件上传/下载的内部 API 直调以 rag/file 事件留痕，不产生 tool_call 事件（该路径仍须通过用户身份校验与 (agent_id, kb_id) 勾选校验，未勾选 403——裁定 D-B，用户裁定 2026-09-22）；
  2. 拦截链完整执行：scope 校验→参数覆写→代理执行（顺序与行为见 BFF-07..09）；
  3. 拦截失败（权限不足）时工具调用被拒并返回明确错误给 agent（不静默放行）。
- **数据/依赖提示**：拦截器组件；工具调用审计记录（工具、调用方、token、动作、结果、时间）→ trace（T01）；内部服务调用路径的身份/勾选校验依赖 BASE-07 租户隔离与 agent 配置关联表。

### BFF-07 简易 agent：代码层面拦截 LangChain Tool 回调
- **描述**：简易 Agent 场景：BFF 在代码层面拦截 LangChain 的 Tool 执行回调。对应 BRIEF §2-BFF「简易 Agent：BFF 在代码层面拦截 LangChain 的 Tool 执行回调」（G04）。
- **来源**：【用户明确要求】（G04）
- **验收要点**：
  1. 简易 agent 对话中触发工具调用（如文件上传、知识库检索），实际执行前经过 LangChain 回调拦截点（trace 可见拦截事件）；
  2. 拦截点内完成 scope 校验 + token 注入（BFF-08/09）；
  3. 直连底层工具库绕过回调的路径不存在（架构文档说明工具只经拦截注册）。
- **数据/依赖提示**：LangChain callback/interceptor 钩子；工具注册只走拦截入口。

### BFF-08 第三方 agent：拦截 HTTP 响应中的 Tool Call 意图
- **描述**：第三方 Agent 场景：agent 返回 Tool Call 意图后，BFF 拦截该 HTTP 响应。对应 BRIEF §2-BFF「第三方 Agent：agent 返回 Tool Call 意图后，BFF 拦截该 HTTP 响应」（G05）。
- **来源**：【用户明确要求】（G05）
- **验收要点**：
  1. 第三方 agent 返回工具调用意图（HTTP 响应）时，BFF 拦截该响应、不直接透传给客户端；
  2. 拦截后由 BFF 执行工具（代理执行，BFF-09），结果回传 agent/客户端；
  3. trace 可见：第三方响应→拦截→代理执行→结果返回的完整链路；
  4. 黑盒验收依赖 mock 第三方 MCP server + mock 第三方 agent（按 DECISION-008 协议实现）；mock 资产在开发阶段完成，列为开发→测试交接检查项（测试侧 P2-7，2026-09-22 确认）。
- **数据/依赖提示**：第三方协议中 tool call 意图的表达约定（设计文档明确）；拦截器对响应的解析/改写能力。

### BFF-09 拦截动作：Scope 校验 + 强制覆写参数（token 注入）+ 代理执行
- **描述**：拦截动作三步：①校验 Scope 权限；②强制覆写参数——将 Access Token 强制注入工具参数，防止数据越权（mcp 工具或接口会统一校验 access token 的权限，这是业务系统本身的权限校验机制）；③代理执行——BFF 使用自己的机器凭证调用真实的 MCP Server 或业务 API，再将结果返回 Agent。对应 BRIEF §2-BFF「拦截动作」三条（G06）。
- **来源**：【用户明确要求】（G06）
- **验收要点**：
  1. Scope 不足：agent 调用超出其 scope 的工具 → 拒绝并返回权限错误（可构造：用低权限 token 的 agent 调高权限工具）；
  2. 强制注入：工具实际收到的参数中 access token 为 BFF 注入的用户 token（非 agent 自带）——可验证：篡改 agent 传入的 token 参数，工具收到的仍是用户真实 token；
  3. 租户越权防护：工具按 token 内 tenant_id 校验，agent 无法通过参数篡改访问他租户数据（如让 agent 传别的 tenant_id 被覆盖/拒绝）；
  4. 代理执行：BFF 用自身机器凭证调用真实 MCP Server/业务 API（远端收到的凭证是 BFF 机器凭证而非用户 token——抓包/日志可验证），结果正确返回 agent；
  5. 业务系统侧凭注入 token 做自身权限校验（MCP 工具/业务 API 侧校验逻辑生效）。
- **数据/依赖提示**：工具 scope 元数据（工具→所需 scope）；BFF 机器凭证（配置文件/密钥管理，不落业务表）；工具调用审计（trace）。

### 8.1 验收要点汇总
1. 全部请求经 BFF：无 token 401、超流控 429、路由正确、OpenAI 兼容格式可被标准 SDK 直接调用（BFF-01..04）。
2. chat 请求 token 解析出 tenant/user/scopes；普通员工与管理员对同一 agent 集合的访问差异符合权限配置；跨租户拒绝（BFF-05）。
3. 简易 agent 工具调用走 LangChain 回调拦截、第三方 agent 走 HTTP 响应拦截，均无绕过路径（BFF-06/07/08）。
4. 拦截三动作可分别验证：scope 不足拒绝、token 强制注入（篡改无效）、BFF 机器凭证代理执行且租户越权被防（BFF-09）。

## 9. 模块九：Trace + 检索（TRACE）

### TRACE-01 全链路 trace 记录
- **描述**：记录 agent 每个会话的交互内容（包含上传文件、生成的文件等）、工具调用、RAG 调用、时间点、耗费 token 等。对应 BRIEF §2-Trace「记录 agent 每个会话的交互内容……耗费 token 等」（T01）。
- **来源**：【用户明确要求】（T01）
- **验收要点**：
  1. 一次完整对话（含文件上传/生成、工具调用、RAG 检索）后，该会话的 trace 可查，且包含：每轮交互内容（用户/assistant 消息）、文件事件（上传的文件、生成的文件，含文件引用）、工具调用（工具名、参数摘要、结果摘要、耗时）、RAG 调用（查询、命中 chunk、分数）、时间点（各事件时间戳）、token 耗费（各轮/各模型调用及会话合计）；
  2. 简易与第三方 agent 的会话均记录（第三方：平台侧可见的交互与拦截事件）；
  3. trace 与会话/消息实体可互查（会话详情可展开 trace，trace 可定位到会话）。
- **数据/依赖提示**：trace 事件实体（会话引用、事件类型（message/file/tool/rag/system）、载荷 JSON、时间点、token 数、关联工具/文档引用）；按会话聚合；依赖各模块事件上报。

### TRACE-02 trace 数据检索
- **描述**：提供对 trace 数据的检索功能。对应 BRIEF §2-Trace「检索功能（对 trace 数据的检索）」（T02）。
- **来源**：【用户明确要求】（T02）
- **验收要点**：
  1. 可按条件检索 trace：时间范围、用户、agent、会话、事件类型（工具调用/RAG 调用）、关键词（消息/工具参数内容）；
  2. 检索结果可下钻到具体事件详情（含完整载荷、时间点、token）；
  3. 检索受租户隔离约束（只能检索本租户 trace）。
- **数据/依赖提示**：trace 检索索引（关键词/全文、时间、租户、agent 维度）；依赖 TRACE-01 数据。

### 9.1 验收要点汇总
1. 任一含文件/工具/RAG 的会话，trace 五要素（交互内容、工具调用、RAG 调用、时间点、token 耗费）齐全可查，且含文件事件（T01）。
2. 多维条件检索 trace 并下钻到事件详情，租户隔离生效（T02）。
3. 会话详情 ↔ trace 双向可定位（AGENT-04 的对话详情展示过程信息即基于此）。
